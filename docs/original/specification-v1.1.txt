1. Resumo executivo
Orbit será uma plataforma pessoal de operações que reúne tarefas, hábitos, finanças e treinos em uma única experiência. Embora o produto seja de uso individual, a solução deve nascer multiusuário, com isolamento rigoroso de dados, para demonstrar fundamentos de SaaS, segurança por objeto e arquitetura escalável sem introduzir microsserviços prematuramente.
A recomendação é construir uma API em Python com FastAPI, PostgreSQL e SQLAlchemy 2, consumida por uma aplicação React com TypeScript e Vite. A combinação é coerente com o objetivo de mostrar versatilidade além de PHP/Laravel, preservando sinais profissionais já relevantes: APIs REST, modelagem relacional, Docker, CI/CD, React, testes e ownership ponta a ponta. FastAPI gera OpenAPI a partir de tipagem Python e o ecossistema atual mostra forte interesse no framework; React continua oferecendo o sinal de mercado mais amplo entre React e Svelte para vagas full-stack [R1–R6].

Sequência recomendada
Não comece desenhando todos os módulos nem todas as tabelas. Entregue fatias verticais completas: fundação → identidade → tarefas → hábitos → finanças → treinos → dashboard → hardening → bot Telegram. Cada fatia precisa conter migration, regra de domínio, endpoint, tela ou canal de entrada, testes, telemetria e documentação.

2. Visão de produto e limites
2.1 Problema a resolver
Pessoas que organizam tarefas, hábitos, finanças e treinos em ferramentas distintas perdem contexto e não conseguem enxergar o dia ou o mês como um sistema único. Orbit centraliza planejamento, execução e histórico, permitindo responder perguntas como: “o que preciso fazer hoje?”, “quais hábitos estão pendentes?”, “quanto da próxima fatura já está comprometido?” e “qual foi minha última carga neste exercício?”.

3. React ou Svelte: decisão de frontend
Svelte oferece excelente experiência de desenvolvimento e menos cerimônia, mas React é a escolha mais inteligente para este portfólio. O objetivo não é apenas construir a aplicação; é maximizar legibilidade para recrutadores e alinhamento com vagas full-stack internacionais. A pesquisa Stack Overflow 2025 mantém React como tecnologia central no movimento de desenvolvedores que desejam ampliar atuação full-stack, enquanto o ecossistema oficial de React, TypeScript, Vite e TanStack cobre bem uma SPA orientada a dados [R1, R4–R6].

Decisão
Usar React + TypeScript com Vite. Não usar Next.js no MVP: a aplicação é autenticada, tem pouco valor de SEO e já possui um backend REST dedicado. Vite deixa essa fronteira explícita e reduz complexidade acidental.

3.1 Estado no frontend
TanStack Query para estado remoto: cache, invalidação, sincronização, paginação e mutations.
React Hook Form + Zod para formulários e validação de experiência; o backend continua sendo a autoridade final.
Context apenas para autenticação, tema e preferências globais pequenas.
Não usar Redux por padrão. Introduzir Zustand ou Redux Toolkit somente após um caso concreto de estado cliente compartilhado e complexo.
Gerar tipos/cliente TypeScript a partir do OpenAPI para reduzir divergência entre backend e frontend.

4. Estratégia arquitetural
4.1 Monólito modular
Orbit deve ser implantado inicialmente como uma única API e um único banco PostgreSQL, mas o código será dividido em módulos de domínio com dependências explícitas. Essa solução preserva transações locais, simplifica desenvolvimento e deploy e, ao mesmo tempo, demonstra arquitetura. O custo operacional de microsserviços não é justificável para uma pessoa desenvolvendo um produto de portfólio.

Figura 1 — Arquitetura de containers proposta.
4.2 Fronteiras dos módulos

Figura 2 — Context map simplificado. O dashboard compõe leituras; módulos não alteram tabelas uns dos outros diretamente.
Cada módulo possui camada de domínio, aplicação, infraestrutura e API. A regra de dependência é de fora para dentro: FastAPI e SQLAlchemy conhecem a aplicação; o domínio não conhece o framework. Essa separação deve ser pragmática: entidades simples não precisam de classes artificiais, e abstrações só entram quando protegem uma regra ou uma fronteira real.
4.3 Princípios de desenho
Princípio
Aplicação no projeto
Vertical slices
Cada funcionalidade atravessa banco, domínio, API, tela, testes e telemetria antes da próxima.
DDD pragmático
Agregados e value objects apenas onde há invariantes: Money, compra parcelada, fatura, rotina e sessão.
CQS
Commands alteram estado; queries retornam DTOs. Não adotar CQRS distribuído.
Transação por caso de uso
O application service abre e fecha a transação; repositórios não realizam commit oculto.
Contratos explícitos
OpenAPI, schemas Pydantic, erros RFC 9457 e tipos gerados no frontend.
Evolução orientada por evidência
Redis, worker, cache e materialized views entram quando uma necessidade mensurável aparecer.

4.4 O que não fazer
Criar um “BaseRepository” genérico com dezenas de métodos que esconda SQL e regras de consulta.
Permitir que rotas FastAPI executem lógica financeira ou façam commit diretamente.
Compartilhar modelos ORM como schemas de entrada/saída da API.
Criar dependências cíclicas entre módulos; usar interfaces de aplicação ou eventos internos.
Extrair um microsserviço apenas para “mostrar conhecimento”. A decisão deve nascer de escala, ownership ou isolamento operacional real.

7. Padrões transversais de domínio e API
7.1 Identificadores e ownership
Usar UUID gerado pela aplicação para recursos públicos; nunca expor IDs sequenciais como autorização implícita.
Toda tabela de domínio pertencente ao usuário contém user_id ou é alcançável por uma relação que permita verificar ownership.
Todo repositório recebe o user_id no método; “buscar por id” sem proprietário não deve existir na camada de aplicação.
Índices compostos começam por user_id para consultas dominantes e isolamento lógico.
RLS do PostgreSQL pode ser introduzido como defesa adicional na fase de hardening, sem substituir testes de autorização.
7.2 Dinheiro
Nunca utilizar float/double para valores monetários.
Persistir amount_minor como BIGINT e currency como código ISO 4217. Em Python, expor um value object Money e usar Decimal apenas nas fronteiras de conversão.
O sinal não fica no valor: amount_minor é não negativo; tipo/direção define entrada, saída ou transferência.
Operações entre moedas ficam fora do MVP; transferências exigem a mesma currency.
Somas e rateios devem ser testados por propriedade: a soma das parcelas sempre precisa ser exatamente igual ao total.
7.3 Datas, horas e timezone
Timestamps técnicos em UTC com timezone; preferências do usuário armazenam um timezone IANA, por exemplo America/Sao_Paulo.
Datas de competência, vencimento e check-in são DATE local, não timestamp UTC.
Mudança de timezone afeta cálculos futuros; datas históricas locais já registradas não são reescritas.
Injetar Clock na aplicação para testes determinísticos de “hoje”, fechamento, vencimento e streak.

7.5 Auditoria, arquivamento e imutabilidade
Audit events registram actor, ação, entidade, timestamp, request_id e mudanças relevantes; não registrar segredos ou token.
Capturas do Telegram registram update_id, estágio de processamento, payload extraído, lançamento resultante e correções; o áudio bruto é descartado após o processamento e nunca é gravado em logs.
Dados financeiros que já impactaram uma fatura fechada não são apagados: usar ajuste, cancelamento ou estorno.
Templates de treino podem mudar, mas sessões concluídas preservam snapshots do nome, posição, descanso e metas.
Tarefas e hábitos podem ser arquivados para manter histórico sem poluir listas ativas.
8. Identity & Access
8.1 Estratégia de autenticação
Não implementar armazenamento de senha e recuperação de conta do zero. Use OpenID Connect com Authorization Code + PKCE. No ambiente local, Keycloak sobe pelo Compose; em produção, o provedor pode ser Cognito, Auth0 ou outro compatível. O frontend recebe tokens pelo fluxo OIDC e a API valida assinatura via JWKS, issuer, audience, expiração e scopes.
Componente
Responsabilidade
Provedor OIDC
Login, MFA opcional, recuperação, sessões e emissão de tokens.
React
Iniciar PKCE, manter estado autenticado, renovar conforme SDK e nunca persistir token em localStorage sem necessidade.
FastAPI
Validar JWT, converter sub em user profile interno e aplicar autorização por recurso.
PostgreSQL
Persistir user_profile, preferências e dados; não persistir senha do OIDC.

8.2 Autorização
MVP possui role user; role admin é apenas operacional e não deve permitir leitura irrestrita de dados pessoais pela aplicação.
Autorização por objeto é obrigatória: possuir token válido não autoriza acessar qualquer UUID.
Scopes podem separar read/write em futuras integrações, mas não precisam criar complexidade na primeira interface humana.
Endpoints de exportação e exclusão da conta exigem reautenticação ou confirmação forte.

9.2 Regras de negócio
Título obrigatório entre 1 e 160 caracteres após trim.
Status: todo, in_progress, done ou cancelled. done e cancelled são terminais para cálculo de atraso.
Completar define completed_at; reabrir limpa completed_at e volta para todo ou in_progress conforme comando explícito.
overdue é derivado quando due_at < agora e status não é terminal; não persistir esse boolean como fonte de verdade.
Uma due date no passado é permitida para importação e planejamento atrasado; a interface deve sinalizar.
Reordenar tarefas é uma operação em lote limitada à mesma lista e protegida por versão quando houver conflito.
Arquivar remove das listas padrão, mas preserva histórico e auditoria.
Recorrência e lembretes ficam para a fase 2, evitando misturar o motor de recorrências financeiras com tarefas cedo demais.

11.2 Bases de relatório: competência e caixa
O produto deve deixar explícito qual visão está sendo exibida. Na visão de competência, uma parcela aparece no mês da fatura a que pertence, representando consumo/compromisso. Na visão de caixa, o saldo bancário muda quando a fatura é paga. O pagamento da fatura não pode ser contado novamente como nova despesa na visão de competência; ele é a liquidação de uma obrigação já reconhecida.
Evento
Competência
Caixa
Compra parcelada
Reconhece cada parcela no respectivo ciclo.
Não movimenta conta bancária.
Pagamento de fatura
Liquida obrigação; não soma despesa novamente.
Sai da conta escolhida na data do pagamento.
Despesa no débito
Reconhece no período definido.
Movimenta a conta ao ser postada.
Salário previsto

11.3 Compras parceladas
Entrada canônica: total_amount + installment_count. O sistema calcula as parcelas; installment_amount manual é opcional e precisa ser consistente.
R$ 1.500,00 em 12 parcelas gera 12 × R$ 125,00. Informar R$ 75,00 produziria R$ 900,00 e deve resultar em 422 ou em remoção do campo manual.
Rateio em centavos: base = total // count; o resto é absorvido pela última parcela. Exemplo: R$ 10,00 / 3 = R$ 3,33 + R$ 3,33 + R$ 3,34.
A soma das parcelas é uma constraint de domínio validada antes do commit e coberta por property-based tests.
Compra e todas as parcelas são criadas em uma única transação de banco; falha parcial não é permitida.
Repetir o POST com a mesma Idempotency-Key retorna o mesmo recurso, sem duplicar parcelas.
11.4 Algoritmo de ciclo da fatura
Calcular a primeira closing_date igual ao próximo dia de fechamento que seja maior ou igual à purchase_date.
Se o dia configurado não existir no mês, usar o último dia do mês; a interface deve informar essa regra.
A due_date é a primeira ocorrência do due_day estritamente posterior à closing_date: pode ser no mesmo mês ou no mês seguinte.
Compra em ou antes do fechamento entra no ciclo calculado; compra depois entra no próximo. Essa convenção determinística é documentada, pois bancos reais podem variar no dia exato.
Cada parcela seguinte avança um ciclo mensal de fechamento/vencimento, não apenas “30 dias”.
A fatura é criada de forma lazy/upsert para o par credit_card_id + closing_date, protegido por unique constraint.
Pseudocódigo do rateio exato
def allocate_installments(total_minor: int, count: int) -> list[int]:    if total_minor <= 0 or count <= 0:        raise InvalidInstallmentPlan()    base, remainder = divmod(total_minor, count)    amounts = [base] * count    amounts[-1] += remainder    assert sum(amounts) == total_minor    return amounts

11.6 Receitas, salário e recorrências
Regra recorrente armazena frequência, intervalo, data inicial, data final opcional, template de valor, conta e categoria.
Ao criar, gerar ocorrências planned para um horizonte configurado, por exemplo 12 meses; job posterior estende o horizonte.
Marcar uma ocorrência como posted representa recebimento/pagamento real e permite ajustar valor sem alterar o template.
Editar regra afeta apenas ocorrências futuras planned; histórico posted não muda.
Pausar regra cancela a geração futura, não apaga ocorrências já realizadas.
Receita extra pode ser avulsa ou outra recorrência; relatórios distinguem planned, overdue, posted e cancelled.
11.7 Transferências e saldos
Transferência cria duas pernas ligadas e atômicas: saída na origem e entrada no destino.
Transferência não conta como receita nem despesa em relatórios consolidados.
No MVP, origem e destino usam a mesma moeda; câmbio é não objetivo.
Saldo atual = opening balance + movimentos posted. Saldo projetado adiciona planned até a data consultada.
Não armazenar saldo mutável sem necessidade; se materializado no futuro, manter mecanismo de reconciliação.

12.3 Regras de sessão
Iniciar uma sessão a partir de rotina copia ordem, nomes, descanso e template de séries; mudanças futuras na rotina não alteram o histórico.
Por padrão, permitir apenas uma sessão in_progress por usuário; oferecer retomar ou cancelar antes de iniciar outra.
Uma série concluída exige repetitions ≥ 0 e load ≥ 0; séries isométricas/tempo podem ser extensão posterior.
Série de aquecimento, normal, drop set e falha são tipos explícitos; recordes ignoram aquecimento por padrão.
Após concluir uma série, completed_at inicia o descanso. Em reload, o frontend calcula remaining = completed_at + rest_seconds − now.
Finalizar sessão exige pelo menos uma série concluída; sessão vazia deve ser cancelada.
Editar sessão concluída é permitido com auditoria e recálculo dos recordes afetados.
Exclusão de exercício usado em histórico vira arquivamento; referências antigas permanecem válidas.
12.4 Desempenho anterior
Ao abrir um exercício na sessão, buscar a última sessão completed do mesmo usuário e exercício.
Retornar séries ordenadas, carga, reps, tipo e data; opcionalmente restringir à mesma rotina por filtro.
A API retorna previous_performance junto da sessão ou por endpoint dedicado para evitar N+1 no frontend.
Não preencher automaticamente a série atual com a anterior sem deixar explícito; oferecer botão “copiar último treino”.

14.1 Convenções
Nomes de tabelas e colunas em snake_case; plural consistente.

14.3 Estratégia de migrations
Cada PR que altera schema inclui migration, teste de upgrade e, quando aplicável, estratégia de backfill.

14.4 Performance e índices
Analisar EXPLAIN ANALYZE para queries da dashboard e históricos antes de adicionar cache.
Evitar N+1 com selectinload/joinedload deliberado ou query DTO; não ativar eager loading global.
Cursor composto por data + id em históricos para ordenação estável.
Índices parciais para sessão ativa, tarefas não arquivadas e transações abertas quando justificável.
Definir statement timeout e limites de pool adequados ao ambiente; telemetria do pool deve ser observável.

15.2 Async com propósito
Usar async no boundary HTTP e acesso ao banco porque a carga é I/O-bound. Não transformar funções de domínio puras em async. O ganho de portfólio não vem da palavra-chave async, mas de compreender pool, cancelamento, timeout e não bloquear o event loop com CPU ou bibliotecas síncronas.
15.3 Exemplo de caso de uso

17. Segurança e privacidade
A segurança deve se apoiar no OWASP API Security Top 10, principalmente autorização por objeto, autenticação, consumo irrestrito de recursos, configuração e inventário de endpoints [R12].

Controle no Orbit
Broken Object Level Authorization

Broken Authentication

CORS allowlist, headers seguros, docs internas configuráveis, debug desativado em produção.
Injection
Queries parametrizadas via SQLAlchemy; whitelist de sort/filter; nenhuma concatenação SQL de entrada.
Sensitive data exposure
TLS, secrets manager, logs redigidos, backups criptografados pelo provedor.
Supply chain
Lockfiles, Dependabot/Renovate, pip-audit, npm audit, CodeQL e imagem base mínima.
Webhook spoofing e replay
Secret token do Telegram, conversa privada vinculada, update_id único, rate limit e processamento idempotente.

17.1 Controles específicos
Não registrar descrições financeiras completas, tokens ou payloads sensíveis em logs de produção.
Aplicar Content Security Policy no frontend e proteção contra clickjacking.
CSRF é tratado conforme o mecanismo de token/cookie escolhido; documentar a decisão no ADR de autenticação.
Uploads não fazem parte do MVP; ao entrar, validar tamanho, MIME real, armazenamento externo e URL assinada.
Exportação de dados em job assíncrono com link expiring e autorização revalidada.
Exclusão de conta deve ter política clara de retenção/auditoria e não prometer conformidade legal sem revisão específica.

23. Integração de despesas por áudio no Telegram
Esta será a única funcionalidade de IA no escopo atual. O bot não atuará como assistente geral e não consultará tarefas, hábitos ou treinos. Ele receberá uma nota de voz, transcreverá o áudio, extrairá um comando financeiro estruturado e o enviará ao módulo Finance, que continuará responsável por autorização, cartões, categorias, parcelas, faturas e auditoria. Exemplo: “Gastei 50 reais no cartão de crédito Santander com comida” → BRL 50,00 no cartão Santander, categoria Alimentação e data local da mensagem. O resultado é salvo no banco do Orbit e refletido nas telas financeiras; CSV permanece apenas como exportação, nunca como segunda fonte de verdade [R19–R21].
23.1 Jornada do usuário
Etapa
Comportamento
Vincular conta
No Orbit, o usuário gera um código de uso único e envia /connect <código> em conversa privada com o bot. O código expira e não pode ser reutilizado.
Enviar áudio
O usuário envia uma nota de voz, por exemplo: “Gastei 50 reais no cartão de crédito Santander com comida”.
Receber e enfileirar
O webhook valida o secret token, identifica a conexão, deduplica update_id, persiste o inbox e responde rapidamente ao Telegram.
Transcrever e extrair
O worker baixa o arquivo, converte quando necessário, transcreve e produz um ExpenseCapture aderente a um schema Pydantic.
Resolver entidades
A aplicação associa cartão e categoria exclusivamente entre os registros do usuário; o modelo nunca fornece autorização nem grava diretamente.
Registrar ou esclarecer
Com todos os campos resolvidos sem ambiguidade, o gasto é criado automaticamente. Caso contrário, o bot pergunta apenas o dado faltante e não cria registro parcial.
Confirmar e corrigir
O bot devolve valor, categoria, cartão, data e parcelas, com ações de Editar, Desfazer e Abrir no Orbit.
Fluxo técnico: Telegram → webhook → inbox/idempotência → fila → transcrição → extração estruturada → resolução de entidades → comando Finance → PostgreSQL → resposta do bot.
23.2 Arquitetura e responsabilidades
O adapter Telegram recebe Update e CallbackQuery; handlers traduzem protocolo externo para comandos, sem conter regras financeiras.
O webhook usa HTTPS, valida X-Telegram-Bot-Api-Secret-Token, aceita somente os update types necessários e rejeita chats que não sejam privados ou vinculados [R19].
telegram_updates funciona como inbox com UNIQUE em bot_id + update_id; redelivery devolve sucesso sem repetir efeitos.
O webhook persiste/enfileira e responde rapidamente. Um worker Celery executa download, conversão, transcrição, extração, retries e resposta ao usuário.
SpeechToTextPort e ExpenseExtractorPort isolam o provedor. A implementação inicial recomendada usa OpenAI File Transcription e Structured Outputs com Pydantic [R20, R21].
O worker usa FFmpeg apenas quando o formato recebido precisar ser convertido para um formato aceito pelo serviço de transcrição.
O extrator retorna apenas dados candidatos — amount, currency, instrument_hint, category_hint, occurred_on, description e installment_count — sem IDs internos.
Resolvers determinísticos validam ownership, aliases e unicidade de cartões/categorias; somente depois o application service chama o comando existente do módulo Finance.
PostgreSQL continua sendo a única fonte de verdade. Áudio, modelo e Telegram não acessam tabelas diretamente e não contornam invariantes de fatura ou parcelamento.
TelegramClient envia recibos, perguntas e botões; falhas depois do commit usam outbox/retry para responder sem repetir o lançamento.
23.3 Regras de negócio e ambiguidades
A integração segue regras restritas para que conveniência não reduza a confiabilidade financeira:
A primeira versão aceita somente despesas enviadas por nota de voz em conversa privada por um usuário previamente vinculado.
Campos mínimos: valor positivo, moeda, data, descrição, categoria e meio de pagamento. BRL, data local da mensagem e uma parcela são defaults quando não houver indicação contrária.
Para cartão de crédito, o resolvedor precisa encontrar exatamente um cartão ativo do usuário. Se houver dois cartões Santander, o bot apresenta opções e aguarda uma CallbackQuery.
O modelo sugere category_hint; a aplicação escolhe apenas categorias existentes do usuário. “Comida”, por exemplo, pode resolver para o alias Alimentação. A IA não cria categorias automaticamente.
Auto-registro ocorre somente quando valor, direção, meio de pagamento, cartão/conta e categoria atingem critérios de resolução definidos e avaliados. Ausência ou conflito leva a awaiting_clarification.
“Em 12 vezes” utiliza o mesmo caso de uso de compra parcelada da API; soma, fechamento, vencimento e faturas continuam obedecendo às invariantes financeiras existentes.
update_id é a chave de deduplicação externa; o comando financeiro recebe Idempotency-Key derivada da captura para garantir efeito único no domínio.
Depois do commit, o bot envia um recibo. Editar usa os endpoints normais do Finance; Desfazer executa cancelamento, estorno ou ajuste conforme o estado, nunca exclusão silenciosa de histórico.
Áudio bruto é mantido apenas em armazenamento temporário durante o job e removido ao final. Transcrição e payload extraído têm retenção configurável, ficam fora de logs e são visíveis somente ao proprietário.
Limites de duração, tamanho e frequência são menores que os limites externos e configurados por ambiente; abuso ou arquivos inválidos falham antes de consumir o provedor de IA.
23.4 Modelo de dados e estados
A integração pode ser implementada com quatro tabelas próprias, mantendo o módulo Finance independente do Telegram:
telegram_connections — user_id, telegram_user_id, chat_id, status, linked_at e revoked_at; IDs externos em BIGINT e unicidade por bot.
telegram_link_tokens — token_hash, user_id, expires_at, consumed_at e attempts; token de uso único, curto e nunca armazenado em texto puro.
telegram_updates — bot_id, update_id, chat_id, message_id, file_unique_id, status, attempts, last_error, received_at e processed_at.
voice_expense_captures — telegram_update_id, user_id, transcript, extracted_payload JSONB, resolved_card_id, resolved_category_id, confidence metadata, transaction_id e failure_code.
Estados principais: received → queued → transcribing → extracting → resolving → posting → posted. awaiting_clarification pode retornar a resolving; failed, cancelled e reversed preservam histórico e motivo.
23.5 Contratos e endpoints
POST /api/v1/integrations/telegram/link-tokens — gera um código temporário para o usuário autenticado.
GET /api/v1/integrations/telegram/connection — informa status, bot configurado e data da última atividade, sem expor token.
DELETE /api/v1/integrations/telegram/connection — revoga a conexão e invalida capturas ainda não processadas.
POST /integrations/telegram/webhook — endpoint externo separado da API do usuário; autenticação pelo secret header e validação da conexão armazenada.
Callbacks de escolher cartão/categoria, cancelar e desfazer usam payload opaco e curto que referencia uma captura pertencente ao chat vinculado.
23.6 Testes, avaliações e observabilidade
Dataset versionado em português brasileiro com valores em reais, aliases de bancos/cartões, categorias, datas relativas, parcelas, ruído, pausas e transcrições imperfeitas.
Teste canônico: “Gastei 50 reais no cartão de crédito Santander com comida” deve produzir amount_minor=5000, currency=BRL, direction=expense, instrument_hint=Santander e category_hint=Alimentação.
Testes unitários cobrem schema e resolvers; integração cobre inbox, ownership, transação Finance e outbox; E2E usa fixture de Update e providers falsos para ser determinístico.
Casos negativos obrigatórios: secret inválido, usuário não vinculado, chat em grupo, arquivo excessivo, valor ausente, dois cartões compatíveis, categoria inexistente, redelivery e falha após commit.
CI não depende de chamadas reais. Um smoke test manual ou agendado pode validar Telegram e o provedor em ambiente protegido, com orçamento e credenciais separados.
Métricas: latência por estágio, custo por captura, taxa de auto-registro, taxa de clarificação, falhas, retries, correções/desfazimentos e divergência encontrada nas avaliações.
Logs e traces usam IDs e status; nunca incluem áudio, bot token, API key ou transcrição completa em produção.
23.7 Fora do escopo desta integração
Não haverá chat aberto, perguntas sobre dados pessoais, resumo semanal, recomendação financeira, planejamento de treino, alteração de tarefas/hábitos, geração de dieta, resposta por voz, RAG, embeddings ou banco vetorial. A IA existe apenas para transformar uma nota de voz de despesa em um lançamento financeiro validado.

Conclusão
Orbit é um projeto de portfólio forte porque combina quatro domínios com tipos distintos de complexidade: workflow, calendário, transações financeiras e histórico de execução. A integração Telegram adiciona uma fronteira externa real — webhook, fila, áudio, extração estruturada, idempotência e observabilidade — sem conceder autonomia irrestrita à IA. A arquitetura maximiza o que pode ser avaliado sem transformar o repositório em uma demonstração artificial de infraestrutura.
A disciplina mais importante será controlar o escopo. Uma aplicação menor, completa e profundamente testada terá mais valor de mercado do que quatro módulos incompletos. O caminho recomendado é entregar primeiro a fundação com tarefas e, depois, usar hábitos, finanças e treinos para demonstrar progressivamente decisões mais sofisticadas.
Direção final
React + TypeScript, FastAPI, PostgreSQL e monólito modular são as escolhas-base. A profundidade do projeto estará nas regras de parcelas/faturas, streaks, snapshots de treino, ownership, idempotência, testes de propriedade, OpenAPI, CI/CD e observabilidade. A única IA será um pipeline delimitado de despesas por áudio no Telegram, demonstrando integração externa e processamento assíncrono sem transformar o produto em um agente genérico.
